## Goal in one paragraph
Slice 5 of part A turns the unit rewrite into something that can be undone, and adds the only automatic deletion Sigma may ever perform. While the upkeep gate is open, the engine's unit push (`_pushed`) also creates a backup ref of the OLD unit tip under refs/sigma/backup/<unit>/<UTC timestamp> in the same atomic push as the leased unit update (both or neither). A restore verb puts a named backup back, with a lease on the tip the pass produced, so it refuses if the remote moved. A prune deletes backups older than 14 days while keeping the newest 5 per unit, selecting by the literal prefix only (and reading any former product prefixes the rename registry knows), and is the one sanctioned autonomous deletion. A unit name that would make the ref longer than 255 bytes is refused loudly. The same change edits the deletion rule (the branching rules document, section 13b) and the irreversible-action prose (a carve-out covering only the prune and the existing lease force-push, net-neutral inside the measured phase payloads), updates the never-delete guard's exact-site pin and the write-surface inventory, shows every new behaviour red before green, and changes nothing while the gate is closed. The recorded acceptance for #921 has five bullets. Where each lands: (1) atomic backup and restore, BR-1 to BR-5, M1, M5, T-1, T-2, T-5; (2) the prune, BR-5, BR-6, BR-8, M3 to M5, T-3, T-4, T-13; (3) the over-long name refusal, BR-3, BR-10, CV-2, CV-3, M2; (4) the rule edit, the carve-out, the pin and the inventory, BR-16 to BR-21, BR-34 to BR-38, T-6 to T-8, T-12; (5) red before green, the closed gate and the verify command, BR-24 to BR-28, T-9 to T-11.

## Measurements
All on local bare remotes, one machine, git 2.49.0 unless stated; times are wall-clock milliseconds (ms) or seconds (s) as labelled, sizes in bytes (B); "median of N" where repeated, single run otherwise.

**M1. Atomic backup plus leased rewrite.** Row 1 is the intended push: one atomic push carrying a lease on the unit branch at the old sha, the new head as the branch update and the old sha as a second refspec onto the backup name; it succeeded in 41 ms (single run) and created no local ref. State of the backup name before the push, with and without a second lease `--force-with-lease=<backup ref>:` (empty expectation, meaning the name must be absent):

| Backup name holds | Without the extra lease | With the extra lease |
| --- | --- | --- |
| nothing | rc 0; branch moved; backup is the old tip | rc 0; same |
| an ancestor of the old tip | rc 0; the name is silently fast-forwarded to the old tip; branch moved | rc 1 (stale info on the backup); the whole push refused; branch unmoved |
| an unrelated commit | rc 1 (non-fast-forward); whole push refused | rc 1 (stale info); refused |
| a descendant of the old tip | rc 1; refused | rc 1; refused |
| the same sha | rc 0; no-op for that ref; branch moved | rc 0; same |

The same 10 cases gave identical outcomes on git 2.54.0. Other rows: a stale lease on the unit branch (another writer pushed first) gave rc 1 with the other writer's commit intact and no backup created, so the existing classification (remote tip differs from the leased sha means lease refused) stays correct; the same name collision WITHOUT --atomic gave rc 1 but the branch DID move and no backup was made, which the classification would misread as a lease refusal, so --atomic is load-bearing; a server with receive.advertiseAtomic false gave rc 128 ("the receiving end does not support --atomic push") and moved nothing; a server denying non-fast-forward pushes refused the atomic push and the legacy push alike (no new failure mode); a server pre-receive hook that rejects every ref outside heads gave rc 1 with the branch unmoved while the legacy push on the same server gave rc 0 (a NEW failure mode: every pass would fail until the block is turned off); a server hiding the namespace (transfer.hideRefs) listed 0 refs and rejected a backup push with "deny updating a hidden ref"; a client pre-push hook that allows only heads saw both refspecs on its input, refused the atomic push (branch unmoved) and allowed the legacy push, and a linked worktree uses the same hooks directory.

- T-2 One-second stamps collide (M1). Under --atomic a collision refuses the whole push (the pass fails safe, the branch unmoved); without it the branch moves and no backup exists. The extra expect-absent lease turns a silent fast-forward of an ancestor-holding name into a refusal. Whatever is chosen, tests must inject the stamp: the engine has only a monotonic clock seam (`skills/sigma-loop/scripts/feature_rebase.py:821`), so the stamp and the prune's "now" need an injectable wall clock. Restore creating its own backup within the same second as the pass collides too.
- T-3 The prune's "literal prefix" must be enforced by the caller (CV-11, M5): list, then keep only names that start with the exact prefix, have exactly one unit segment (the unit rule) and one fixed-width stamp segment; everything else is kept, never deleted. An unreadable listing is not an empty one (the live-branches reader returns None for the first and an empty set for the second, `skills/sigma-loop/scripts/feature_sync.py:495-531`): a failed listing deletes nothing and says so. A behavioural proof like the finish and merge tests: feed the planner a list containing a unit branch, a branch named like the prefix, a lookalike prefix, a tag and a name with extra segments, and assert no delete-shaped call names them.
- T-4 Age comes from the stamp (CV-12). Unparseable, malformed and future-dated names are kept; rank by the fixed-width stamp (string order is time order). Clock skew matters because the stamp is the writer's clock: a future-dated name sorts as newest, so it would occupy a keep slot and push real backups below the cut, and any writer to the remote can create one. Exclude future-dated names from the ranking and keep them. Group per raw unit component (CV-5).
- T-5 Restore is a delete-capable shape (M5 control): validate the source as 40 lowercase hex and the unit with the unit rule before building the refspec; add a never-empty proof like the existing one (`tests/test_no_autonomous_feature_branch_deletion.py:553-589`). Restore is itself an unbacked rewrite (the produced tip is then unreferenced): decide whether it backs that tip up in the same atomic push. Take the per-unit rebase lock (`skills/sigma-loop/scripts/feature_rebase.py:357-376`) and report busy when held. A restore does not stop the next pick from rewriting the unit again, because the restored tip is behind its base again (read from `_rebase_pass`, not run): document it or add a hold, which is new state.
- T-6 Guard cascade and placement (M7). The pin goes from 6 to 8 (code in feature_rebase.py) or 9 (new module). A second ":refs/" line in feature_rebase.py breaks the unpack test whatever the line layout (A2 shows putting both refspecs on one line does not help once restore is in the file, and doing it to dodge the proof would game it). A new module keeps that test passing but needs a script-help entry, a fold-inventory classification for its loader, and a non-trivial import of the gate. Use the visible forms: `--delete` for the prune, a literal ":refs/" line for each refspec; a dynamically built colon-empty prune is invisible to the guard (C) and is a pinned known limit. Keep each new build site in its own function so the pin names it.
- T-7 Inventory (M7). Four new rows, sorted into place, with the real gate text, not regenerated (regeneration would stamp the file default). The ratchet compares counts, so `_pushed` must keep exactly one push call site or its two rows change to count 2 (D). The documented CI gesture is the control to run.
- T-8 The pinned sentence (BR-18, M9). Section 13b is the natural home; list the file in the guard's set so it must stay verbatim, and keep every other mention of the rule at one or two shared 4-grams. The README and enforcement prose must not reuse the clause.
- T-9 "Nothing changes while the gate is closed" has two halves the existing tests cannot prove. (a) The legacy argv: existing tests check a substring only (TD-5) and the pick-cost helper's pass fails before the push (TD-6), so a new test must reach `_pushed` with a recording runner and compare the argv byte for byte when the block is absent, false, the text "true", the number 1, and enabled-but-invalid; the slice-1 near-enabled lists (`tests/test_upkeep_proof.py:13-52`) are reusable. (b) The OPEN path: `tests/test_upkeep_proof.py:160-175` requires the pick-time call list under `{"enabled": true}` to equal the closed list, so the open path may add NO git call anywhere up to and including the tree comparison that precedes `_pushed` (a collision probe, a backup listing or a lookup in `_rebase_pass` or `_rebase_feature` would turn it red; a call inside `_pushed` is not reached by that world and is safe for this pin). The name-length check is a pure string test and fits.
- T-10 Registering a gated entry point (the recommended way to reuse the slice-1 zero-footprint harness for the verbs) forces: the note rewrite (BR-26), the edit of `test_note_phrases`, a driver in `tests/upkeep_support.py`, and the constant "upkeep" staying out of every other shipped file (the CLI verb names `restore` and `prune` are fine). A gated verb returns a closed result, not a push; the pick-time backup is a plain gate query inside `_pushed`, not a decorated function.
- T-11 Red-to-green binding (the gate's rules): selectors come from the plan's tests section (1 to 25 backticked bullets); the whole file of every planned node is hashed and a red counts only if the file is byte-identical at green; only assertion failures count; captured output turns the traceback attribution off, so planned tests must be silent (captured subprocesses, bounded timeouts, no prints, no skips) and unparameterised, and names that do not exist yet must be read with a getattr and asserted. So: new tests in NEW files; edits to existing pins (the guard file, the inventory, `tests/upkeep_support.py`, `tests/test_upkeep_tmpl.py`) belong to the code step and must live in files that hold no planned node; do not reopen slice 2's two test files. Part 1 (tests only) is followed by a recorded red, then Part 2 (code), then a green; stage the plan, research, acceptance and design files before the green verify so the exposure scan sees them. A committed plan or research record is capped at 131,072 bytes (`tests/test_b6_462.py:34-35`), so pin long test bodies by hash, not verbatim. Two more hygiene rules bite new and edited tests: a subprocess.run with a literal timeout under 60 s that names the repository root is itself a failing test (`tests/test_no_short_whole_repo_scan_timeout.py:20-50`), so the ratchet-gesture control needs a limit of 120 s or more; and the advisory tamper scan (`skills/sigma-loop/scripts/tamper_scan.py:40-60`, `:95-125`) counts a removed assert line (an assert whose text changes counts as removed), an added skip or xfail marker and a new assert ending in "is not None", so edits to the existing pins should change data lines, not assert lines.
- T-12 Text budgets (M8, CV-21). The deletion rule and most carve-out sites sit outside every measured payload, so the carve-out can live in the README, the enforcement table (regenerate the page) and the scaffold, with the six measured sites left untouched or edited net-neutral (Q11 before and after). Do not touch the loop skill file at all (26 characters of room).
- T-13 Scale (M3, M4). Chunk the delete by an argument-byte budget derived from the platform (the machine's limit divided by a safety factor, with a hard ceiling far below it), use a per-ref lease, no --atomic, and cap the deletions per invocation so a wrong listing cannot take a namespace in one run; at 1 to 3 ms per ref a first prune of a 10,000-ref backlog takes 30 to 40 s locally, longer over a network, so it must resume across runs. State the ceiling: no serialised chokepoint is added (the per-unit lock covers a pass; the prune needs none because the per-ref lease makes a changed ref survive).
- T-14 Hosting-side failures (M1): a host that rejects, hides or caps the namespace, or lacks atomic push, fails the whole push, so unit upkeep FAILS on every pass. This needs a stated recovery (turn the block off; the closed gate restores the legacy push) and an honest message (TD-7); never fall back silently to a push without a backup.
- T-15 Outcome plumbing (BR-3): the new refusal outcome joins OUTCOMES, IN_CLAUSE and _WORDING; the doctor row is deferred (BR-43).
- T-16 Other rewriters stay unbacked (TD-9); the documentation must not claim "every rewrite".
- T-17 Client hooks (M1) see the backup refspec and a heads-only pre-push hook refuses the whole push; the hooks policy is slice 6, so slice 5 ships with hooks on and this limit documented.
- T-18 Former prefixes (CV-6): the pinned sentence is scoped to refs/sigma/backup/; a prune that also deleted under a prefix the predecessor may still own (it can run beside Sigma) is a deletion of refs we may not own, and the owner's rule allows exactly one named prune. Keep the list empty until a real former prefix exists, and prove the mechanism with a planted prefix.
- T-19 Documentation honesty (AGENTS.md reliability): until the scheduler slice nothing calls the prune unattended, so "the one sanctioned autonomous deletion" is a rule about a future caller; say so. The documented gesture must be the tested one (`tests/test_documented_gestures.py`): spell each verb and flag in USAGE.
- T-20 Test cost: the guard group runs in 16 s, the engine and hygiene group in 196 s; the whole suite was not timed here. Plan the verify command accordingly.
- T-21 Recovery for each failure mode (AGENTS.md resiliency), all grounded in the measurements above: a job killed during the atomic push leaves the remote untouched and the next pass redoes it; a same-second collision fails the pass with the branch unmoved and the next pass, after the clock ticks, succeeds; a host refusal needs the lever in T-14; an interrupted prune is idempotent (a deleted ref deletes again with rc 0 and a warning) and a ref changed since the listing survives; a restore refused after the remote moved is re-run with the new tip; an unreadable listing deletes nothing. Nothing in this slice runs in the background, so liveness is the scheduler slice's.

## Constraints & unknowns
- Unverified: everything about the hosting service (CV-35, CV-36, CV-40, CV-41); the git 2.34 floor (CV-37); the argument limit of a platform with a short command line (CV-38); whether the predecessor ever wrote backup refs (CV-39); the full-suite duration; timings are single-machine, local-transport figures and say nothing about network cost (the per-ref advertisement adds roughly 84 bytes per ref per push on the wire, not measured).
- Blocking (needs a decision before the plan is fixed; a conservative default is stated so the plan can proceed if it is confirmed):
  1. Where restore gets "the tip the pass produced". The acceptance requires a lease on it; the design's dependency list leaves out the per-unit state that would hold it (CV-9, CV-28); the backup name format was resolved as prefix, unit and UTC timestamp only (B-4). Options: (a) an explicit expected-tip argument supplied by the person running restore from the pass's JSON output (default; no new store, no name change); (b) encode a short form of the produced tip in the backup name's leaf, which would also remove same-second collisions but changes the resolved name format and costs about 8 bytes of the 220; (c) a persisted record, which is the state slice's job and a new store with a growth disposition; (d) lease on the remote tip read at restore time, which does not protect against a push made after the pass. Default taken: (a), with the name unchanged and a collision refused loudly.
  2. The content of "former product prefixes" the prune reads. The acceptance says the prune also reads them; the registry knows none and nothing shows any was ever written (CV-6, CV-39); deleting under a prefix a still-installed predecessor may own conflicts with the owner's one-named-prune rule (T-18). Default taken: an empty list with the mechanism and a planted-prefix proof; the owner adds a prefix only on evidence.
- Non-blocking (decide in the plan):
  1. Register the verbs as gated entry points (recommended: reuses the zero-footprint harness; costs BR-24 to BR-26) or query the gate directly.
  2. Placement: new module versus feature_rebase.py (T-6); the unpack tests are the deciding cost.
  3. Whether restore is gated at all. Default: both verbs use the project door, and a closed result names the plain git fallback; the argument for leaving restore ungated is that a person who turned the block off after a bad rewrite still needs the lever.
  4. Whether restore backs up the produced tip (default yes, same atomic push).
  5. The prune reads `backup.keep_days` and `backup.keep_last` from the gate's settings (default, so the knobs are not dead) rather than constants.
  6. Prune cap per invocation and the byte budget (T-13); default a few hundred refs.
  7. Per-unit grouping by raw component (default) or by folded unit (CV-5).
  8. Name for the over-long-unit outcome, and the wording; the doctor row is deferred to slice 7 (BR-43).
  9. Which "existing lease force-push" the carve-out names: the engine's unit-tip push only (default) or also the goal-branch pushes at `skills/sigma-loop/scripts/work.py:3954` and `:4007`, which are also unattended.
  10. Whether to split this goal along its natural seam (create path with refusal, guard and inventory; then restore, prune and the rule edits); the lane is large and both halves touch the same pin and inventory, so a split costs two pin updates.
  11. Name and ID of the growth disposition entry (BR-32) and its unscanned flag.
