# Research: Yielding-shell safety: reviewer receipt liveness + bounded wait + agent-thread cap
**Goal**: #1551 (Agrim-Intelligence/sigma#1551) · **Lane**: medium · **Date**: 2026-10-16

## Goal in one paragraph
`reviewer.py run` pre-writes `outcome: failed, failure: not_completed` before `Popen` and replaces it only on completion. A host whose shell yields (Codex `exec_command`) reads that placeholder as a dead reviewer and parks `reviewer_down`. Make the receipt say `running` (pid, started_at, run nonce, deadline), have readers tell running-and-live from crashed, add a bounded `wait` verb, make the loop prose use it, and treat a Codex agent-thread cap as a capacity wait with retry, never a park.

Windows/pid portability: `run_review` refuses on non-POSIX at reviewer.py:853-855, so the WRITER only exists on POSIX; `os.kill(pid, 0)` is valid. Readers (gate verbs) can in principle run on Windows (windows.yml CI runs `tests/test_windows_real.py` only, .github/workflows/windows.yml:27; ci.yml is the main matrix) but a receipt can only have been written on POSIX. Reuse ledger.pid_alive (ledger.py:1967-1996; fail-toward-alive; PermissionError->True): on Windows os.kill(pid,0) TerminateProcess hazard is documented in watch_daemon.py:71-80, so the reader must not call os.kill there; route win32 through watch_daemon's `_win32_pid_alive` (watch_daemon.py:223) or simply treat "running + win32" as running until deadline. Pid reuse: ledger/state liveness already pairs pid_alive with an mtime TTL backstop (state.py:649-665). Recommended here, stronger and portable: running-live := pid_alive(pid) AND now < deadline (started_at + review.timeout_seconds + grace), because the runner itself kills the reviewer at timeout (:926-930) so a legitimate run can never outlive it. That bounds any reused-pid impersonation to timeout+grace without reading process start times. Optional extra: compare `ps -o lstart= -p <pid>` captured at launch; macOS and Linux both have it; /proc is Linux-only. Not required for correctness given the deadline.

Unkillable design nuance: the recorded pid must be the RUNNER's own (`os.getpid()`), not the reviewer child's: the child is `start_new_session=True` (:918-920) and its death is the runner's business; the runner dying leaves the child orphaned, which `communicate` timeout no longer polices (known; existing behaviour).

## Constraints & unknowns
- North-star: `north_star.py` printed `absent` for this worktree (drop-in project); not a lane signal.
- Budget (measured, `python3 evals/phase_context_budget.py`, 2026-10-16): ceilings are down-only and "may not be raised to absorb growth" (evals/phase_context_budget.json). Headroom in est_tokens: orchestrator 32387/32403 (16 tokens, ~160 words), goal-slot 12432/12437 (5), research 3006/3012 (6), plan 1206/1260 (54), plan-review 3637/3661 (24), implement 3050/3050 (0), review-pre-pr 6227/6243 (16), review-post-pr 6305/6310 (5), retro 3886/3934 (48). In practice any net-added prose line breaks the gate in orchestrator/goal-slot/review phases. Therefore: (a) put the guidance in the tool's own output (reviewer.py run prints one stderr line immediately at launch: "running pid N; if this call yields, `reviewer.py wait ...`" : visible in a yielded call's output, zero context cost, host-agnostic); (b) change existing prose words 1:1 (e.g. replace running.md:138 "(a fresh `process` ... --phase plan_review|review)" text) and offset with trims; measure with the same command. skills/sigma-loop/SKILL.md is 252 lines vs LINE_LIMIT 500 (evals/skill_structure.py:100); skill_budget_waivers.json has zero waivers, so lines are fine and the payload ratchet is the binding constraint.
- Unverified: whether Codex keeps the yielded `exec_command` session alive after the orchestrator's turn ends (the measured case shows it survived >=45s). If the host reaps it, pid dies and the receipt correctly reads failed/crash.
- Non-blocking: should `wait` also exit 0/1/2 by verdict? Proposal: exit 3 = RUNNING (distinct from 0 final, 1 failed/no-approve, 2 usage), prints `RUNNING pid=... elapsed=...s deadline_in=...s`; final prints verdict line and the reviewer's stdout is NOT replayed (only the receipt's verdict/hashes exist; the output is not stored). Open: the yielded run's stdout is held by the runner; `wait` can return verdict but not the findings text. Plan must decide whether to persist output next to the receipt (new bounded file) or tell the agent to read the yielded session's final output. Smallest: verdict only, since record verbs need the receipt, not the findings; but the maker needs findings to act on a block, so persisting `output` (capped, same lifetime as receipt, cleared by clear_receipts) is likely required. Flag as the main design call.
- Blocking: none.
- Thread cap: Sigma cannot observe the host's spawn tool. What is enforceable: (1) a contract in prose that a spawn error matching a capacity message is retried with bounded backoff, never `record parked`; (2) an audit row via existing `loop.py log .sdlc "$goal" action --act "capacity wait: ..."` (actionlog.py:161-199; `agent_done --result` is free text so a `capacity_wait` result needs no schema change). Not enforceable: that the model actually retries; no code sees the failure. A code-side option is a small `loop.py capacity-wait` verb that logs the row and prints a backoff delay/attempt count and refuses (exit 2) after N attempts, so the "bounded" part is machine-counted; that is a +~60 line addition with its own tests and is the optional half. Park remains legitimate only after the bound is exhausted, using the existing `unknown` qkind (qkind.py:19); do NOT add a new qkind (QKINDS is a closed list tied to docs/label-model.md and unpark.py:160-166, which would widen the blast radius).

## Split recommendation
Split. Receipt liveness (reviewer.py, gates, tests) and the thread-cap rule share no code, no test, and no failure mode: one is a state-machine bug in the reviewer receipt, the other is a host-capability contract Sigma cannot observe. The thread-cap half is mostly prose (budget-constrained, unenforceable beyond an audit row) and should not delay or widen the receipt fix. If kept as one goal, land receipt liveness first; the cap prose goes in the same PR only if it fits the budget by 1:1 replacement.
