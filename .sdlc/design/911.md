## Intent
Make keeping unit branches current an optional, off-by-default capability of one engine: a scheduler that rebases a unit
when it has drifted far enough (or a backstop expires), bounded conflict resolution that proves its result before
pushing (or parks with a ready brief), and a landing that a person asks for and that merges exactly what was verified —
with every existing path byte-identical while the feature is off. Premises that moved: Sigma already rebases units at
pick time (on by default), from the CLI, from the attended skill and from chat, so the gap is scheduling, unit-level
resolution and one shared set of checks — not "only at pick time" (PC-19); a unit conflict stalls only that unit, not
everything (PC-20); chat already lands units without approval, so landing is not merely "hand-run" (PC-22); the watch
daemon runs on Windows, so the job must refuse there rather than inherit a POSIX-only daemon (PC-24); and nothing checks
a git version or that every config key is in the template today (PC-25, PC-26).

## Queries run
Recorded verbatim by the sweep, per round and area. Display pipes (`| head`, `| cut`) are kept where they were run; a
leading `cd <repo> &&` is stripped. Reads that were not searches (`python3 -I -B` range prints, in-memory probes of a
module's own functions) are listed at the end of each area. Two regexes are respelled so that tests which read this file
as shipped markdown do not mistake them for links or file paths: in the round-1 README search for `feature` followed by
a unit word, a one-character class directly followed by a group is written as an alternation (the class-then-group
spelling parses as a markdown link); and in the round-3 search for `.get("kind")` readers, the escaped dot before `py`
is written as a one-character class (a quoted word ending in an escaped `py` extension parses as a dangling file path).
Each respelling selects exactly the same lines (checked by running both spellings over the tracked tree).

## Doubts
- **D-1.** (inherited `open_squash_landing`) **Resolved against the code**: repositories that squash-merge goal PRs are in
  scope and their arrivals are already classified by the trailing `(#N)` subject (PC-27); rebase-merge repositories stay
  declined (the engine reports them UNVERIFIABLE today); unit landing always uses a merge commit; a unit someone
  squash-lands onto main by hand is invisible to an ancestry test and is caught by the landed-unit skip through a merged
  landing PR whose head equals the unit tip. Still open: GitHub's default squash title for a single-commit PR may carry no
  `(#N)` (D-16). Settle with a squash-landing fixture in the engine slice.
- **D-2.** Tick integration. Recommended: an in-process decision step in `tick()` (the `rotate_log` precedent) that
  starts a detached job only when due. Alternatives: fold into the drift step, or a ninth `TICK_CALLS` row (breaks the
  tuple pins and adds a subprocess per tick when off). The watcher reads config once at start and exists only while the
  ledger is on, so enabling needs a watcher restart and a ledger-off clone has no scheduler.
- **D-3.** Cross-clone exclusion without a lease: two opted-in clones can both work one unit. The push lease prevents a
  clobber but not duplicate fetch/replay/verify or duplicate resolver spend, and it protects pushes only — the landing
  merge needs its own head pin. Is a dedicated lease (a new ledger kind, with a contract bump) worth adding later?
- **D-4.** The default numbers (window 21 d, burst 24 h, target 12 h, floor 3, ceiling 40, cooldown 2 h, backstop 24 h,
  dormant 14 d → 72 h, verify timeout 60 min) were derived on the predecessor's history. This repository is linear and
  squash-only and cannot host the re-derivation; measure on an adopter repository with units.
- **D-5.** Hooks are off during the replay and for a clean-replay push, on after a resolved conflict. For adopters'
  repositories this is a consent decision: documented as part of the project opt-in, or a separate switch?
- **D-6.** An unattended verify needs per-checkout git-local trust (`sigma.allowRepositoryShellCommands`); a fresh clone
  refuses. Readiness row plus documentation; never granted on the operator's behalf.
- **D-7.** The `--onto` anchor. Recommended: store the cut-from sha in the goal record when the worktree is cut (it is
  stored nowhere today). Relying on the backup ref of the old unit tip fails for a goal idle longer than the 14-day prune.
- **D-8.** Recomputed acks live in a per-machine runtime file, while the tracked ack store is team-wide by design; a
  second clone re-derives its own.
- **D-9.** Resolver CLI flags. Already used somewhere in the tree: `-p`, `--max-budget-usd`, `--permission-prompts none`,
  `--disallowedTools` (list form), `--output-format json`, `--model` (aliases), `--permission-mode` (bench only).
  Unverified here: `stream-json`, `--verbose`, `--max-turns`, `--restricted`, `--strict-mcp-config`, `dontAsk`,
  `--tools`, per-path `Edit(...)` allows, `mcp__*` patterns, `--settings` with `disableAllHooks`,
  `--no-session-persistence`, `--disable-slash-commands`. Probe them against the installed CLI before the resolver slice.
  Also open: excluding the scratch worktree's own `.claude/`, `.mcp.json` and agent instruction files, and the auth and
  billing of an isolated config directory.
- **D-10.** Codex-only and Cursor hosts have no `claude` CLI: Level 2 is unavailable there and conflicts park. Is a Codex
  resolver route a later slice?
- **D-11.** `doctor features` prints a row for every optional feature, "off" included. Recommended: print the upkeep row
  only when the block exists, so an absent block changes no output.
- **D-12.** Rule edits reach new adopters only: the scaffold is skip-if-exists, the Codex block refreshes only when
  `--codex` is re-run, and `migrate.py` has no refresh path.
- **D-13.** A merge's exit code proves nothing (exit 0 on an already-merged or merely queued PR). Landing decides from
  the read-back: the merge commit's second parent is the verified commit and the merge happened after the attempt began.
  Whether the CLI/REST returns 0 on an enqueue or an armed auto-merge is unverified.
- **D-14.** Merge-queue repositories: `merge_queue_enable` configures a SQUASH queue, which contradicts "merge the exact

## Detailed design
**What already exists, corrected.** Sigma already rebases units: the pick-time pass (`work.rebase_upkeep`, ON by default),
the CLI `upkeep` verb, the attended `/sigma-rebase`, and chat `--rebase` (a driven headless session) (PC-1, PC-19). A unit
conflict stalls only that unit's upkeep, and goal-level CHANGELOG conflicts already resolve themselves (PC-20). Landing is
the attended helper plus chat `--unsafe-merge`, which already lands without a person's approval (PC-22); neither pins the
head, reads the merge back, or can land a unit twice (PC-6). What is missing is: a schedule, unit-level conflict
resolution, a safe repeatable landing, and ONE set of checks shared by every door. The design adds those behind a gate
and leaves every existing path byte-identical while the gate is closed.

**1. The gate, and its precedence over the existing switch.** One total module (proposed `feature_upkeep.py`, named
`feature_*` so the unit-key case-fold inventory covers it, BR-108) is the only reader of the new `upkeep` block. It never
raises: a missing, non-dict or mistyped block reads as disabled; a per-key schema table (type and range) runs before any
cross-check (floor ≤ ceiling, cooldown ≤ backstop ≤ dormant backstop); `enabled` must be the boolean `true` (`"true"`,
`1`, `"yes"` are disabled); an unrecognised `conflicts.resolve` reads `"off"`; a placeholder model id keeps the resolver
closed. Three opt-ins: the project (`upkeep.enabled: true` in the committed config), the machine (a new
`POST_RENAME_ENV` variable, proposed `SIGMA_UPKEEP_JOB`, registered in `legacy.py`, BR-89, plus `ledger.enabled`), and
spend (`conflicts.resolve: "agent"` with finite per-run and per-day caps). Precedence:

| Door | `upkeep` absent or disabled | `upkeep.enabled: true` |
| --- | --- | --- |
| Pick time | exactly today (`work.rebase_upkeep` decides; ON by default) | today's trigger, with the engine's new checks; `work.rebase_upkeep: "off"` still turns this door off |
| Scheduler | does not exist; no new subprocess, file or output | decision step + bounded job (§3) |
| A person's request (rebase now / land) | today's attended skill unchanged | the engine (§4, §6) |
| Chat (`--rebase`, `--unsafe-merge`, `--list`) | unchanged | the engine, the marker and the registry reader (B-5) |

The "nothing changes" contract is proven, not asserted: a recording trap over every new entry point under an empty
config, the shipped template and a near-enabled matrix (`"true"`, `1`, `"yes"`, enabled without the machine switch,
without the ledger, a typo'd resolver value) sees zero subprocess, network or model calls and no new files, while a
fully enabled control sees attempts; the existing pick-cost pin (BR-69) stays green; a static guard proves the gate is
the first call in each new entry point. The template gains the block (BR-57) and a discoverability pin (BR-72); existing
adopters never receive it (skip-if-exists), so absent means off forever unless they add it.

**2. Measuring drift and deciding what is due.** One measure module computes, for a unit: behind/ahead against the base,
and drift = PR arrivals on main the unit lacks + PR arrivals on the unit since its last successful pass. An arrival is a
first-parent `Merge pull request #N` commit or a single-parent `(#N)` subject (the existing classifier, BR-4), counted by
AUTHOR date over a history walk bounded by an `-n` cap with the date filter applied in Python — never `--since` alone
(PC-4; settled by a skewed-committer-date fixture). It returns UNKNOWN when the cap is hit before an out-of-window commit,
on any git failure other than a verified not-ancestor, and when commits exist but none classify (rebase-merge
repositories); UNKNOWN never makes a unit due by drift (the backstop still applies). `velocity.py` is not reused (X-34);
the five existing "behind" computations stay as they are (PC-3). Threshold `auto` = (main rate + unit rate) × target
hours / 24, clamped to [floor, ceiling], each rate the max of the window rate and the burst-window rate; an integer
overrides it and `null` turns the drift trigger off. Per-unit state lives in `.sdlc/state/upkeep/units/<unit-key>.json`
(atomic writes, D-26): last attempt, last success, both tips, outcome, next-due reason, consecutive failures. Unreadable
state means overdue and is reported; reads never write. Due rule: cooldown since the last ATTEMPT (default 2 h), backstop
since the last SUCCESS if the unit is behind at all (24 h; 72 h for a unit with no unit-side arrival for 14 days); a
failed or parked pass restarts the cooldown but not the backstop. Units are listed with `feature_registry.read`, never
the derived index (X-33). New stores get growth dispositions (BR-92).

**3. The scheduler: a decision step and one bounded job.** Inside `watch_daemon.tick()`, an in-process step (lazily
imported, wrapped so it can never skip the rest of the tick, BR-21) evaluates the gate before any I/O. Closed: return.
Open: within a per-tick time budget, pick at most one due unit (most behind first), write a status file (last tick,
decision, refusal), and start the job if none is running for this clone. The job is detached with its own session, all
three stdio on DEVNULL (PC-7: an inherited stdout held the call for the child's whole life), an allowlisted environment
with its own run id, an explicit push-guard budget instead of the inherited call timeout (BR-11), a wall-clock cap with
process-group kill, a stop file registered with the stop-file inventory, and a heartbeat refreshed from a poll loop (no
thread). It works only in scratch worktrees, never the main checkout. On Windows the step records one refusal in the
status file and the doctor shows it (D-18); the job never starts there. Revival is the daemon's own (PC-23); a unit with
no active goals relies on the daemon staying up, and the doctor's overdue row is the backstop for a missed trigger.

**4. One pass (the engine, behind the gate).** Existing checks stay, in order (BR-2), plus a landed-unit skip: the tip
is contained in the base, or a merged landing PR's head equals the unit tip (the API path is what catches a squash
landing, D-1); a landed unit is never moved to main's tip (PC-5). The engine runner (BR-87) sets
`GIT_TERMINAL_PROMPT=0`, `GIT_EDITOR=true` in the environment (it outranks `-c core.editor`, PC-11),
`rebase.updateRefs=false`, `commit.gpgsign=false` and per-command timeouts; a stopped rebase with no unmerged paths is a
FAILED outcome, never filed as a conflict. Hooks are off during the replay (they fire per replayed commit) and for a
clean-replay push (no new code), and on for a push after a resolved conflict (new code) (D-5). Every push uses an
explicit-sha lease (`--force-with-lease=<branch>:<sha>`), never a `+` refspec or `--force`; the old tip goes to
`refs/<product>/backup/<unit>/<UTC timestamp>` in the SAME `git push --atomic` as the leased unit push (both or neither;
B-4, D-25). `restore` puts a backup back with a lease on the tip the pass produced and refuses if the remote moved. The
prune deletes backups older than 14 days, keeping the newest 5 per unit, by literal prefix only — the one sanctioned
autonomous deletion (followup in the Dossier), widened into the never-delete guard (BR-66) and named in the branching
rules (BR-60). The pass records both tips at start and re-reads them before the resolver, before verify and before the
push (at most 2 restarts). Acks are recomputed after every rewrite into a runtime union file under
`.sdlc/state/upkeep/` (the tracked store cannot be rewritten in the root checkout, BR-17; D-8). Idle goal branches are
replayed with `git rebase --onto <new unit tip> <tip the goal was cut from>`, the cut tip being recorded in the goal
record when the worktree is cut (BR-84, D-7); evidence is re-anchored only after mechanical (Level 1) changes or a green
verify (BR-16); a refused push to a goal branch already deleted after its PR merged is a skip with a reason. Outcomes go
to the per-unit state and, as UNADDRESSED `note` entries keyed `upkeep-<unit-key>` with an `upkeep:<outcome>:<sha12>`
ref, to the shared ledger — written in-process with `ledger.safe_append`, never through `loop.py note` (which arms a real
claim) and never addressed (which would wake the inbox and autowatch) (BR-105, BR-106; checked in round 3 against every
consumer). The job writes as the clone's pinned ledger actor so that its notes publish (BR-107, D-23); pinning the
actor does not stop the inbox cursor gaining a key per run, so slice 7 also picks a writer that adds none (BR-104,
D-33).

**5. Cross-clone exclusion.** No ledger lease is added. Correctness across clones is the explicit-sha lease on every push
(binding decision 3); on one machine the existing per-unit flock serialises the doors that take it — the engine and the
chat door do, and the attended door (`/sigma-rebase`) does not today: it takes no lock and pushes with a bare lease
(BR-34, BR-35), which the job's own fetch re-arms. Slice 6 therefore makes the attended door take the per-unit lock and an
explicit-sha lease while upkeep is enabled (independent review F2); until it lands, the attended door is documented as
not serialised. The ledger notes give the
team-wide daily spend ceiling and let the doctor flag two clones working the same unit within one cooldown. The cost is
possible duplicate work and bounded duplicate spend when several machines opt in (D-3, D-24); the docs recommend one
opted-in machine per set of units.

**6. Conflicts.** *Level 1* (no model): a heading-aware CHANGELOG union — entries land under `## Unreleased`, above any
version heading main added (PC-15) — on the unit path. *Proof gate* (engine, no model) before any resolution is pushed:
`git diff --cached --check` before every `--continue`; commit count, order and subjects unchanged; only conflicted files
differ from a plain replay; a per-commit before/after comparison that covers merge commits; no net loss of tests or
assertions in touched files; the direct-commits check still clean; `verify.command` green through the shared runner
(timeout, group kill, stop file, refuses without trust — BR-79, BR-90); an independent reviewer approves. Anything else
parks. *Stamp*: a Title-Case trailer in the body of every touched commit (subjects untouched, so arrivals stay
PR-traced), registered with the legacy names (BR-89), plus a resolution record stored locally and posted on the tracking
issue. *Level 2* (opt-in, capped): an isolated headless session on Claude-capable hosts only (D-10): flags re-probed
against the installed CLI (D-9), an allowlisted environment, prompt on stdin, the pinned full model id and tier ceiling
from `predict.py` (BR-102), edits limited to the conflicted files, per-run and per-day caps, process-group kill;
eligibility per stop (6 files, 20 diff3 hunks, 800 conflict lines) and per pass (8 stops, 12 files); protected paths,
structural conflicts and conflicts inside a replayed merge park. The independent reviewer is a separate call with a
machine-readable verdict, author-blind, whose brief passes the existing leak gate (BR-97) — the route does not exist
today (B-2). *Level 3*: one finding per conflict (its files and the unit commits it touches), at most 2 attempts, the
issue number stored, created with `target_unit=` (BR-103), closed by the engine through `gh_api` when a later pass
succeeds or the unit lands, and never when the filing reused an existing duplicate (BR-82). Missing CLI, expired login or
a rate limit parks and backs off; a killed run is charged its cap.

**7. Landing (a person's request only).** Preconditions (verify configured; no open direct-commits finding or parked
conflict; nothing else holds the unit; not already contained in main) → a pass now → if any commit carries the resolver
stamp and `land.review_resolved`, show those commits once → verify the rebased tip in a scratch worktree → re-read BOTH
tips (at most 3 attempts, then stop with "a tip kept moving") → merge the exact verified commit with a merge commit
through `gh_api` with a head pin → read the PR back: `merged` only if the merge commit's second parent is the verified
commit and it merged after this attempt began; `armed`/`queued` when the host only armed or queued it; `refused`
otherwise (D-13, D-14). Re-landing works: "landed" means the tip is contained in the base or a landing PR whose head is
this tip merged — not "any merged PR from this head" (BR-38, BR-46, BR-20 change only under the opt-in). The unattended
guard is a conjunction built in Sigma's own code (a supervised-run marker set, OR a live managing loop session without
the exact consent flag the skill passes only when the user's own message asked); when unattended, landing refuses unless
a single-use unit approval marker exists, consumed as the last gate before the merge (B-3). The scheduler can never
land, and no config key changes that. Landing never deletes the branch, marks the unit finished, or uses an admin merge.
The routing rule ("rebase/land unit X" → the request skill) is text in the existing Cursor and Codex rule constants, the
project template and the agent-rules docs — never in `sigma-loop/SKILL.md`, which has about 26 characters of room
(PC-18) — with a test so the copies cannot drift (BR-58, BR-100, D-27).

**8. Guards, ratchets and rule edits land with the code that needs them.** Before any backup/prune/landing code: the
never-delete guard learns the colon-empty refspec, a REST delete of `git/refs/...`, `update-ref -d` and `gh_api` deletes
(BR-66); the write-surface scanner classes push-scoped `--delete`/`:`/`+` refspecs as destructive, sees `update-ref` and
`gh_api` write helpers, and every new site gets an explicit inventory row with its real gate (`upkeep.enabled`), argv
built inline and run through a recognised runner (BR-95, BR-98). New GitHub calls go through `gh_api` (BR-68, BR-88).
Rule edits, each with its pins in the same change and one pinned constant for the new wording: completion is
"human-initiated" rather than "human-only" (BR-61); the landing exception to "nothing merges a feature branch" (BR-62);
the resolver stamp/record/reviewer as the substitute for "every change arrives as a PR", keeping sentence 1
byte-identical (BR-64); the backup-ref exception to the deletion rule (BR-60); a bounded carve-out from the
irreversible-action prose for the prune and the capped resolver (and the existing lease force-push, D-20) (BR-94) — all
net-neutral inside measured payloads (BR-100, D-27).

**9. Doctor and liveness.** Rows appear only when the block is enabled (D-11), probes are bounded and skipped on the
cheap session-start path (BR-99): last tick age read from the upkeep status file's own age (not the watcher heartbeat,
D-17), overdue units (behind for more than twice their backstop), a stalled job (heartbeat age), unreadable state, and
readiness — git version (floor 2.34.0, refuse 2.35.0, through a `requirements()`-gated preflight check, BR-93), verify
trust, resolver prerequisites, backup count. Documented in a reference file, not `sigma-doctor/SKILL.md` (BR-101). A dead
job is distinguishable from an idle one by age alone.

**The five properties.** *Reliability*: every capability is proven by a fixture or the recorded end-to-end run, every
guard is seen red once, and the documented gesture is the one tested. *Scalability*: per-tick cost grows with open
units, not history (one fetch, one batched ahead/behind read, first-parent counts only for units past that gate); the
tick keeps a time budget and resumes; backup refs and state are pruned by age; ledger growth is one note per
state-changing outcome (10x units → 10x notes per day, bounded by the cooldown), written by a writer that adds no
inbox-cursor key and no ledger file per run (BR-104, slice 7). *Resiliency*: a job killed mid-rebase
leaves the remote untouched (the next pass recovers); a push is all-or-nothing with its backup; tips that move restart the
pass; a wrong-but-green resolution is undone with `restore` and found by its stamp; spend, CLI and login failures park and
back off. *Safety*: three opt-ins, limits from config, a resolver with no shell and a scrubbed environment, backups before
every rewrite, one named deletion, and loud refusals where a guarantee cannot be made (git too old, Windows, rebase-merge
repositories, no reviewer route, no CLI, an over-long unit name). *Liveness*: status file, heartbeat and age-based doctor
rows.

**Scope (operator decision, B-1).** This design is built as part A: §1–§5 and §9 above, plus the backup-related rules of
§8 (slices 1–8). §6 (conflicts) and §7 (landing) are the intent and constraints that designs B and C start from; nothing
in part A depends on them, and part A changes no conflict or landing behaviour.

**Sequencing and hot files.** Gate and guards first; measure and state; the verify runner and backup/restore before any
background pusher exists; engine changes; the scheduler; documentation, the opt-in audit and the end-to-end run last.
`feature_rebase.py` is touched by slices 5 and 6 (and later by designs B and C) — at most two live at once; `work.py` by
slice 6; `watch_daemon.py` only by slice 7; the branching rules document by slice 5 (and later by B and C, in order). Use
the strongest model tier for the push, backup, job and audit work.
