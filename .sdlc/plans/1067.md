# Plan 1067: tighten the head-pinned merge helper

## Files
- skills/sigma-loop/scripts/gh_api.py: `_REPO_RE` and `merge_pr_pinned`.
- tests/test_gh_api.py: new tests next to the existing pinned-merge tests.
- tests/test_feature_land_merge.py: one landing-level test.
- CHANGELOG.md: Unreleased entry.

## Behaviour
- `_REPO_RE` gains two negative lookaheads so neither the owner nor the name segment can consist only of dots. Names
  like `.github` or `a.b` still match.
- `merge_pr_pinned` raises `GhApiError` ("malformed merge reply ... no sha") when the reply has no sha (absent or
  null). It no longer accepts a missing sha. `merge_reply_sha` is unchanged.
- In the landing, the raise is classed as a lost acknowledgment, so the outcome comes from the read-back: a pull
  request still open is `unconfirmed:lost-acknowledgment`, never `merged`.

## Test list
- test_repo_pattern_rejects_dot_only_segments: parametrised over `./r`, `../r`, `o/.`, `o/..`, `.../r`; no call made.
- test_repo_pattern_keeps_ordinary_names: `o/r`, `a.b/c-d_e`, `o/.github`.
- test_merge_pr_pinned_rejects_reply_without_sha: `{"merged": false}`, `{"merged": true}`, `{"sha": null}`.
- test_landing_reply_without_sha_is_not_merged: landing-level, open read-back, outcome does not start with `merged`.
- Controls: revert each change once and see the new tests red.

## Risks
- A real host reply always carries a sha on success, so strictness costs nothing; a missing sha with a real merge is
  resolved by the read-back rather than trusted.
- Existing tests that feed a sha-less merge reply to the helper would break; the targeted run covers gh_api and landing.
