## Behaviour
1. Owner ruling (adopted): chat landing routes through the engine and the SAME unit approval. Chat supplies no consent
   flag (it cannot) and passes a driven fingerprint in the environment given to the engine (the existing fingerprint name,
   taken from the approval module, no new name), so the engine requires a local single-use approval bound to the head.
2. Gate closed (`feature_upkeep.enabled` false, or it raises): the old `dispatch` + `_unsafe_merge_check` path, byte-identical;
   nothing from the engine is loaded or called. The listener's own environment is never used to infer "attended".
3. Gate open: claim by unit name (same arbitration as before), run the engine, finish the claim, reply. No chat worktree is
   cut: the engine takes the unit's rebase lock itself and would find a held one busy.
4. Reply mapping: merged, merged-with-warning, already-landed, armed, rehearsal (cannot happen with merge=True; mapped as
   unclear), refused:<reason> (reason and detail, plus how to approve locally when the reason is the guard),
   unconfirmed:<reason> (pending record stays; check the repository), anything unknown: "unclear" text, never "failed".
   Ledger kind: merged/already-landed -> done, refused -> failed, unconfirmed/unknown -> failed with the unconfirmed words.
5. Requester: Slack user ids only (`[UW][A-Z0-9]{2,20}`), else `unknown`; appended to the ledger note as `requested by <id>`
   and echoed in the reply. Not recorded when the gate is closed (byte-identical).
6. Help text and grammar: `--unsafe-merge <name>` unchanged in shape; help text gains one sentence stating that with unit
   upkeep on it needs a local unit approval first.
