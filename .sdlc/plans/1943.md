# Plan #1943 label plan reads a possibly short listing

## Files
- `skills/sigma-loop/scripts/label_drain.py`: `plan()` re-reads the label listing once.
- `tests/test_label_drain_lag_1943.py` (new), `docs/label-drain.md` (one sentence), `CHANGELOG.md` (Unreleased).

## Behaviour
After the first `fetch_issues_rest`, if the listing is empty OR its newest `updated_at` is under `LAG_WINDOW_S` (60) seconds old, wait `LAG_WAIT_S` (3, env-overridable via `SIGMA_LABEL_LAG_WAIT`, 0 allowed) and read once more; union the two reads by issue number. The plan dict gains `lag: {"window_s":60,"reread":bool,"added":[numbers]}`; `render_plan` prints one line naming the possible lag when the window applied. Older listings are read once, no wait. Only one re-read, so cost is one extra REST call and at most a few seconds, never a loop. The MAX_MEMBERS refusal applies to the union.

## Test list
- fake listing returns member B only on the second read: plan sees A and B (red when the re-read is removed).
- old listing (updated_at far past): fetched exactly once, no wait called.
- empty listing: re-read once.
- window clause alone: recent updated_at triggers; empty clause alone: empty triggers (each broken on its own).
- render_plan shows the lag line only when the window applied.

## Risks
Wait is injectable (`sleep` param) so tests do not sleep. No network in tests. Existing plan tests with fake runs counting calls (`test_label_drain_calls.py`) may see one extra call for recent fixtures: set fixture timestamps old or update.
