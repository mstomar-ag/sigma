# Plan #1483: a goal cut while another pass rewrites its unit

## Approach
1. `_cut_tip_fields` records `git rev-parse HEAD` of the new worktree (a `ref` argument, default `HEAD`), for any
   unit base, with the upkeep opt-in off too. `_rerecord_cut_tip` passes `<remote>/<base>` because after a goal
   rebase the unit tip, not the goal tip, is the cut point. Callers keep the same signature.
2. `_rebase_upkeep` notes the engine outcome in a module variable. On a fresh cut from a unit with outcome `busy`,
   `_recut_after_busy` runs after the cut and before the cut tip is saved: fetch the base, compare `<remote>/<base>`
   with HEAD, and if it moved run `git rebase --onto <remote>/<base> <HEAD>` on the still-empty goal branch.
   PROVISIONAL: the no-wait option, chosen over a bounded wait because it adds no stall to the pick door and needs no
   new lock timeout. A push that lands after the re-check is still covered, because the recorded cut tip makes the
   later rebase replay only the goal's own commits.
3. `_rebase_argv` no longer requires the opt-in: a record holding a cut tip that is still an ancestor of HEAD gets
   `--onto`. Records without a cut tip, and goals with no unit base, are unchanged byte for byte.
4. Wording: BUSY clause in `feature_rebase._WORDING`, the `LOCK_TIMEOUT` comment, and `docs/upkeep.md`.

## Test list
- cut_tip is the worktree HEAD even when the shared remote ref has moved, with the opt-in off.
- no cut_tip for a non-unit base; a failed read records nothing.
- two goals of one unit, opt-in off, unit rewritten: the goal's first rebase uses `--onto` and replays only its commit.
- busy start where the remote moved after the cut: goal re-based onto the new tip, cut_tip equals the new HEAD.
- busy start where nothing moved: no rebase call; clause states the situation.
- not busy: no extra git call (byte-identical).
- BUSY clause and docs wording present.
