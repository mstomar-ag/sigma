# Plan 1408: blocking follow-ups inherit the blocked goal's priority; confirmation label never stays on a blocker

## Goal
Three small changes on top of the shared rule (1406) and the source method `raise_blocker_priority` (1407).

## Smaller design (PROVISIONAL)
1. Filing: in `handoff.py` `create_tracked_issue` (and the hand-off open path), when the filing is a blocker (blocks yes) and the mode is not off, the new issue is created with the priority label of the blocked goal when its own is missing, unknown or lower (read the goal's priority once, bounded; unreadable goal means no guess, report and file as before). Never lowered. The confirmation label is never applied to a blocker at filing.
2. Strip: a blocker of an open edge that carries the legacy confirmation label gets it removed with one comment (existing label writers; goal membership is granted only through the existing verdict rule, otherwise stripped only). Call sites: the same places 1407 added (`blockers._act`, the sweep, filing), through one helper on the source.
3. Doctor: `doctor.py` names any blocker that still carries the legacy label or has no priority (a read-only check, existing doctor check shape, mode-gated; off means no output change).

## Test list
- through the real verbs with fake gh: filing a blocker for a P0 goal with none/unknown/P3 own priority creates it at P0; a P3 goal with a P1 blocker leaves P1; mode off byte-identical; the label is stripped with one comment and a second pass writes nothing; doctor names both cases; closed gate output unchanged.

## Risks
Shared files with siblings: single-line calls. No SKILL.md edits. New write shapes must be registered in write-surface inventory and the never-delete guard (reuse existing writers).
