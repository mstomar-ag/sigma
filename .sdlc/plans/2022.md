## Behaviour
- loop._next_untraced (and the next-batch loop over it): find where each candidate iteration lists the backlog (the source's fetch of pending goals, e.g. in sources.GitHubSource); read it once per `next`/`next-batch` call into a payload the candidate loop, the dependency hold, the `--skip` filter and the label filter all reuse. A skipped or held candidate must not trigger a second list.
- Across calls: the list request goes through `gh_api.conditional_get` with a stored ETag PER PAGE (page 1..N; the 200 cap with 500+ goals means every page needs its own ETag), stored under `.sdlc/state/` (atomic write, bounded to the pages seen, fail-open: any trouble -> unconditional read). A 304 means the cached list for that page. Board mode (GraphQL) reads: only the within-call hoist, no ETag.
- The claim path still re-reads the chosen issue's labels before any write (unchanged; a test asserts it).
- Pick order must be identical: a replay test records a fixture backlog (generic issue numbers, labels, blockers) and asserts the pick sequence from the old per-candidate-list code path equals the new one for next and next-batch including held/skipped candidates and `--label`/`--feature` scoping. Generate the expected order from the CURRENT code before changing it.
- No new gh call sites (use gh_api); count requests with the #2019 counter (gh_calls) on a fake runner in the test.
