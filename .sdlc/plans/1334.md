# Plan 1334 - session start: bounded, cached, honest about transient gh failures
Plan sha256: (set by tool)

## Behaviour
1. `hooks/hooks.json` SessionStart entry gets a `timeout` (seconds, 20) so a slow hook can never hold the session.
2. `setup_wizard.wizard_status`: a failing `gh auth` row is the only gh-derived row that can be transient. Retry the doctor check once when the only failing allow-listed row is `gh auth`; if it still fails, keep the row but the step text says "could not confirm the gh login (transient?)" and the fix is "re-run /sigma-doctor"; `gh auth login` advice only when the failure text names a real not-logged-in state is NOT kept (decision: never advise login from the session hook; PROVISIONAL, owner to ratify).
3. Cache: a doctor-lite result with a failing row caused only by `gh auth` is cached for a short TTL (120 s) in the existing wizard cache file (new key `transient_until`), so a second session start inside the window makes zero gh calls. A clean result keeps the 1 h TTL as today.
4. Measure which doctor-lite rows make the 60+ gh calls in github mode with `cheap_only`; skip any not needed for the wizard allow-list (gh calls for non-allow-listed rows are wasted). Smallest change that brings the two session starts under 10 s on a stubbed slow gh.
