# Plan 1941: a landed goal's registry update rides the goal's own commit; the root checkout stays clean

Plan sha256: pending
Feature: rollout-fixes

## Problem (code facts)
`work.py start` calls `_sync_registry` (-> `feature_sync.sync_at_pick`) with the ROOT checkout, which rewrites `.sdlc/features/units/<unit>.json` and `<unit>.md` there and nothing commits them (branching-model §15, #1565). A goal that never lands still leaves membership in the root.

## Design (PROVISIONAL, owner to ratify)
1. `start()` no longer writes the registry in the root: the pick-time membership/reconcile write is made with the GOAL WORKTREE's `.sdlc` as `sdlc_dir` and the worktree as `cwd`, after the worktree exists (so it is a tracked, uncommitted edit on the goal branch). Order of the existing calls in `start()` is kept otherwise; the advisory/never-blocking guard is kept. A resume does not rewrite it.
2. `work.commit` stages it with `git add -A` as today, so the update reaches the unit/base branch through the goal's own commit. A goal that never commits never reaches any shared branch; the root registry bytes are untouched.
3. Concurrency: goals of one unit all amend the same per-unit shard, so rebase/merge can conflict on `.sdlc/features/**`. Add a narrow rescue beside `_try_union_changelog` in `work.py`: when the unmerged set is exactly paths under `.sdlc/features/`, take the upstream version of each (in a rebase `--ours`), re-run the same membership write for this goal in the worktree (idempotent amend, goals are an order-preserving union), `git add`, `rebase --continue`; anything else aborts as today.
4. The cross-repo propagation (`_propagate_registry`) keeps its behaviour; it must not write to the root checkout's registry either (check what it writes; if it only reads the registry, point the read at the worktree).
5. Docs: branching-model §15 bullet "Nothing commits the registry..." rewritten (the first write is still a human's; later picks no longer dirty the root; the old gesture stays for a root already dirty). `docs/launch/write-surface.json` if the inventory lists the root registry write. CHANGELOG `## Unreleased` on its own line.

## Test list
1. Real git fixture: fake remote, start a goal, assert the ROOT `.sdlc/features/` bytes and `git status --porcelain` unchanged; the worktree shows the shard edit.
2. Commit + land (merge into the fake remote's base), then `git pull --ff-only` in the root succeeds and the root registry carries the goal. Red control: call the sync with the root sdlc dir -> root dirty, pull refused / test red.
3. Goal that starts and never commits: nothing in root, nothing on remote.
4. Two goals of one unit started from the same tip; land one, then the second rebases: the shard conflict is rescued and both goals are members. Red control: disable the rescue -> rebase deferred.
5. Rescue refuses when a non-registry path is also unmerged (clause alone) and when a path outside `.sdlc/features/` conflicts.
6. Existing tests: test_dirty_root_registry, test_feature_sync*, test_work*start*, test_feature_registry, test_script_help, write-surface and docs link tests.

## Risks
Shard merge conflicts are now possible in the goal PRs (rescued by 3, else the old "deferred" path). Cross-repo propagation unchanged. `.md` page managed block is regenerated by the same write, so taking upstream then re-amending is lossless for goals recorded by Sigma; hand edits below the managed block on the goal branch would be dropped by the rescue (only upstream's copy wins) -> rescue refuses when the goal branch changed lines outside the managed block? Keep simple: rescue only when the goal's own diff on that path equals what the sync would write (re-run and compare); otherwise abort as today.
