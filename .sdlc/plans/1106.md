# Plan 1106: an applied ask whose status write failed is not re-applied with duplicates

Part of the decision rubric (design 988, slice 19). Feature: decision-rubric.

## Problem
`applier.apply` runs the gesture, appends the decision record, writes the ask file as applied,
then comments. If the status write raises after the record, the ask stays pending; the next tick
repeats the gesture, the decision record and the comment.

## Files
- skills/sigma-loop/scripts/applier.py (`apply` only)
- tests/test_applier.py (one new test)
- CHANGELOG.md (own line under Unreleased)

## Behaviour
Order becomes: gesture, write the ask as applied (rid empty), then the decision record, then a
best-effort rewrite carrying the record id, then the comment. The status write now precedes every
side effect that is not idempotent. If it fails, `apply` returns failed with no record and no
comment; the next tick retries the gesture only (the label swap is idempotent), so no duplicate.
If the later rid rewrite fails the ask stays applied with an empty rid: nothing repeats; a veto
then records without a linked decision id (the veto path already accepts a missing rid).
Closed gate: `tick` and `apply` return before any of this; byte-identical.

## Test list
- status write fails once after the gesture: result failed, zero decision records, zero notes; the
  next tick (write works) applies, and total records and notes are exactly one each.
- existing tests unchanged (applies once, silent, veto, closed gate).

## Risks
- Promote gesture is not idempotent: a retry after a failed status write reports failed each tick
  until the write works; no duplicates, bounded by the daily cap not counting it. PROVISIONAL.
- A crash between the gesture and the status write retries only the gesture.
