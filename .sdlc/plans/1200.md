# Plan 1200: read an owner's "no" so an applied answer can be vetoed

## Files
- skills/sigma-loop/scripts/applier.py: new `read_vetoes`, called at the start of `tick` (apply mode only, only when an applied ask without a veto exists); `apply` veto branch re-parks the issue (swap-label via triage) and comments, once (`reparked` flag), before the level drop.
- tests/test_applier_veto_reader.py: new.

## Behaviour
- Comments come from `comments_fn` (test seam); default is `sources.fetch_comments` when no source was injected or a fake `run` was (so existing tests never hit the network).
- Qualifies: ask state applied, no vetoed_at, now within `window_minutes` after applied_at, comment newer than applied_at, body trimmed lower equals no, author passes `autonomy.is_owner`. Then `answer` records the veto; the same tick plans and applies it.
- PROVISIONAL (owner to ratify): veto period equals the ask window.
- Closed gate: `tick` returns before any read, so byte-identical.

## Test list
- owner no vetoes, lowers level, re-parks, comments, once only
- other text, non-owner, older comment, late comment, unapplied ask: nothing
- closed gate reads nothing; dry run records nothing; comment failure swallowed
- Control: reader call removed turns the first test red (seen).

## Risks
- Real comment read costs up to 3 requests per applied ask per tick, bounded by the window and the daily cap.
